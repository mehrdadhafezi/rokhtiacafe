## Existing invariants and critical risks

The original ordering flow is transactional and uses global advisory lock `LOCK_ORDER_CREATE` to serialize order creation, product inventory reservation in ascending id, a unique `Idempotency-Key` and hashed token-based 24 h tracking. Existing guest ordering must stay functional. For the new accounts, `customer_order_links(order_id PRIMARY KEY, customer_id, created_at)` is immutable and appended only in the SAME transaction as order creation and stock reservation. Staff and customer accounts have separate cookies. Public tracking token is still header-only; never expose it in a URL except a fragment. `customer_label`, IP or `X-Client-Id` are NEVER ownership evidence. Replaying an idempotency key across customers or guest/auth boundaries must never reveal an order or change its owner. Orders/refunds/payments and immutable snapshots must remain unchanged.

CDN/LSWS IP forwarding anti-spoof hardening remains R1 BLOCKED, so no production release despite green CI. Customer identity is unverified at first registration (no SMS/OTP, `phone_verified_at` NULL), and must not be described as verified. No unsafe password-recovery shortcut.
